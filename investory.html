03

성능 검증 및 개선

부하테스트 환경을 구축하고, 측정으로 병목을 특정하고, 구조를 변경한 뒤 재측정하는 순서로 백엔드와 시뮬레이션 서버를 검증했습니다.

3-1 측정 환경

부하테스트 환경 구축

백엔드와 목 증권사 두 서비스에 걸친 시나리오라 어느 레포에도 속하지 않는 독립 프로젝트로 구성했습니다. k6 시나리오 3종(계좌 연동 / 성향분석 / 시뮬레이션)과, 계정 N명 생성 · 거래 이력 생성 · 토큰 발급을 처리하는 프로비저닝 스크립트로 이루어집니다.

  • 실행 환경 2종 — 로컬 Docker 격리 환경(반복 측정용)과, 프로덕션과 동일한 VM 머신타입 · Cloud SQL 티어를 Terraform으로 구성한 GCP 환경(로컬 자원 제약과 외부 네트워크 경로를 결과에서 배제)
  • 공유 DB 격리 — 팀 운영 DB를 가리키는 설정 파일을 어떤 스크립트도 수정하지 않는다는 제약을 두고, 컨테이너 환경변수 우선순위와 부분 오버라이드만으로 격리를 구현
  • 콜드스타트 노이즈 제거 — 서버 기동 직후 부하를 가하면 서버 로그에는 기록이 없는데 응답만 끊겼습니다. DB에는 처리가 완료돼 있어 콜드스타트 아티팩트로 판정하고, 워밍업 단계를 파이프라인에 추가
  • 무증상 실패 확인 — 종목 시드가 없으면 거래가 예외 없이 스킵되고 배치 상태는 성공으로 남습니다. 응답의 적재/스킵 건수로만 드러나므로 시드를 필수 단계로 승격
  • 관측 — 커넥션 풀 상태 로깅, InfluxDB + Grafana 대시보드, 시뮬레이션 서버 Prometheus 메트릭 노출
병목 주체 판별

계좌 연동 p95가 5.25초로 상승했을 때, 인증된 커넥션을 재사용하는 재동기화는 108ms를 유지했습니다. 이 차이로 병목이 본 서비스가 아니라 목 서버의 비밀번호 검증(CPU 바운드)임을 특정했습니다.

3-2 구조 전환

설정 튜닝의 한계를 확인한 뒤 구조를 변경

1000명 동시 요청에서 에러율 15.10%, p95 25.71초로 시작했습니다. 설정을 한 단계씩 조정하며 원인 후보를 배제해나갔습니다.

원인은 구조였습니다. 분석 API가 6개 차원 계산과 외부 호출, DB 쓰기를 요청 스레드에서 동기로 처리했습니다(평균 9~13초). 스레드 수를 늘리면 대기가 분산될 뿐 요청 하나의 처리 시간은 줄지 않습니다.

전환 근거

커넥션 풀을 3배로 늘렸을 때 개선이 40%에 그친 불일치가 판단 근거였습니다. 자원을 늘려도 비례해 개선되지 않으면 병목이 자원이 아닙니다. 이 지점에서 설정 조정을 중단하고 구조를 검토했습니다.

조치와 재측정

  • 동기 201 응답을 202 + job id + 폴링 패턴으로 전환하고 계산을 백그라운드 워커로 이전. 워커 풀 크기를 DB 처리 능력 기준으로 별도 관리하게 되면서 클라이언트 동시 요청 수에 직접 좌우되지 않는 구조가 됐습니다
  • 상태 컬럼과 중복 실행 가드를 추가. 이때 기본값이 기존 이력 전체에 소급 적용되면 새 가드가 기존 사용자 전원을 영구 차단한다는 점을 배포 전에 확인해, 결과 존재 여부로 백필하도록 마이그레이션을 수정
  • 재측정 결과 1000/1000 접수 · 1000/1000 완료. 완료까지 p95는 36.3초로 목표(3s) 미달
  • 추가 분석에서 종목당 시세를 순차 조회하는 N+1을 확인 — 요청 하나가 최대 60회의 순차 DB 왕복. 배치 조회를 추가해 IN절 1회로 대체하고, 두 분석 항목이 결과를 공유하도록 해 중복 조회도 제거
3-3 런타임 특성

시뮬레이션 서버 — async 전환 폐기, 멀티프로세스 채택

커넥션 풀 문제를 해결해 연결 실패는 0건이 됐으나, 50명 동시 요청에서 몬테카를로 500회가 1.98초에서 16.71초로 8~10배 느려졌습니다. DB가 관여하지 않는 순수 CPU 구간이라 GIL 경합을 원인으로 가정하고 두 방향을 측정했습니다.

구성 submit p95 완료 평균 판정
기준선 (단일 프로세스) 1.17s 7~9s —
CPU 구간 프로세스 풀 오프로드 23.45s — 43.27s 대비 완화, 코어 수 내 최적화
DB 계층 전체 async 전환 1.73s — 기준선보다 악화 → 폐기
멀티프로세스 (풀 미조정) 1.5~1.72s 7~11.5s 오버섭스크립션으로 악화
멀티프로세스 + 풀 재배분 0.93s 6.32s 측정한 구성 중 최고

async가 느렸던 이유

이벤트 루프는 프로세스당 스레드 하나입니다. 결과셋 파싱 같은 CPU 바운드 작업이 그 한 스레드에 집중돼 순차 처리됐습니다. 스레드 모델은 GIL 경쟁 비용이 있어도 일부는 여러 코어에 분산되는데, async는 그 여지를 제거합니다. I/O와 CPU가 혼재한 워크로드에서는 async가 스레드 모델보다 불리할 수 있다는 것을 측정으로 확인했습니다.

전환 과정에서 확인한 문제

  • 동기 코드를 스레드로 넘기는 브릿지가 이벤트 루프 스레드와 경합해 응답 자체가 나가지 않는 락업 발생(전원 타임아웃)
  • async 드라이버는 커넥션 반납 시 자동 롤백을 수행하지 않아, 재사용된 커넥션이 오래된 트랜잭션 스냅샷을 유지했습니다. 직전에 생성한 계좌 연동이 조회되지 않아 84%가 조회 실패. 커밋 모드 변경으로 해결
  • 워커 풀 설정이 모두 프로세스 단위 값이라 프로세스 4개 구성에서 4배로 곱해집니다. 코어 수를 프로세스 수로 나눠 배분한 뒤에야 최고 성능이 나왔습니다
  • 멀티프로세스의 선행 조건인 배치 스케줄러 중복 실행을 DB 락으로 단일 프로세스만 실행하도록 정리

폐기한 async 브랜치는 머지하지 않고 기록용으로 남기고, 이슈에 이전 결론을 뒤집는다는 사실과 측정값을 함께 기록해 같은 시도가 반복되지 않도록 했습니다.

3-4 DB 동시성

원인이 서로 다른 데드락 3건

  • 재시도 부재 — 거래매칭 저장이 데드락 발생 시 재시도 없이 실패. 재시도를 추가했으나 그것만으로는 해소되지 않았습니다
  • 수정이 만든 역효과 — 재검증에서 실패율이 16.5% → 43%로 악화. 직전에 도입한 제한 크기 실행기 2개의 큐 포화와, 스케줄러 병렬화가 동시 쓰기 경합을 증가시킨 것이 원인이었습니다
  • 테스트 데이터 구성 — 테스트 종목이 6종뿐이라 저카디널리티 인덱스에 쓰기가 집중돼 데드락이 증폭됐습니다. 30종목으로 확대해 쓰기를 분산. 테스트 데이터 구성이 측정 결과에 직접 영향을 준 사례입니다
  • 락 범위 — DELETE가 계좌와 무관하게 종목 단위 락을 획득해 서로 다른 계좌의 동시 동기화가 충돌 → 계좌 범위로 축소
  • 갭락 — INSERT가 REPEATABLE READ의 supremum 갭락으로 데드락 → 해당 서비스의 격리 수준을 READ COMMITTED로 조정해 해소
3-5 트랜잭션

트랜잭션 범위 축소

  • 동기화 트랜잭션이 외부 서버 호출을 범위 안에 포함해 락 대기 타임아웃 발생 → 조회는 트랜잭션 밖으로, 쓰기만 별도 트랜잭션으로 분리하고 동시 요청 가드를 추가
  • 최초 연동 시 거래 · 보유 적재를 건별에서 배치 처리로 전환
  • 비동기 리스너가 무제한 스레드 생성 실행기로 동작하던 것을 제한 크기 풀로 교체하고, 큐 포화 시 호출자에게 예외가 전파되지 않도록 가드 패턴 적용
